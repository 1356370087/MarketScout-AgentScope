## 修复

1. **保留原题范围。** 研究员与分任务评审收到用户原始条款作为 `scope_context`，继承研究对象和适用场景，同时继续仅对分配的需求 ID 负责。模型生成的简报不能改变这条边界。
2. **按答案选择完整证据。** 写作、评审和修订共用按需求及不同页面排序的证据选择；要求示例时优先完整代码片段。移除写作在相关性排序前再次按旧绑定排列的偏置。真实复验还证明：只按问题排序仍可能漏掉正文实际使用的公式。因此评审先为正文段落选择支持证据，再覆盖研究问题。两份真实库存回放都验证了预算内保留正确公式，不截断证据、不填造事实。
3. **核验真实答案与证据。** 每条 covered 的事实要求必须给出报告中的答案位置及来源见证。评审选择报告片段编号、实际输入中的证据 ID 和来源片段编号，服务端从原文回填摘录，避免模型转抄时改写、漏字或拼接。片段越界、来源未实际提交、缺少事实见证均拒绝；明确未回答的方面不能与 covered 并存。实际提交的证据 ID 随 SQL 模型回执保存、恢复时复用。
4. **核验代码的目的与行为。** 对每个完整 fenced 示例要求预期行为、实际行为、生命周期和判断；从 YAML/JSON 的 `command`、`args`、`entrypoint`、`script` 中提取独立执行单元，避免辅助进程掩盖主任务不能结束的问题。每个单元必须明确预期生命周期和实际停止条件。对完整 `while true`/`while :` shell 循环且未见显式退出语句的窄场景，服务端将实际生命周期校正为持续运行；若该单元要求有限完成，即使模型给出 satisfies/pass，也要求修改。持续服务的正常循环仍可通过。检查是静态核验，不执行报告中的不可信代码，也不宣称能判定任意程序是否终止。
5. **保留恢复兼容性。** 新运行冻结契约升级到 v20，v19 仍按原规则恢复。没有新增数据库迁移、业务配置字段或领域专用放行规则，也没有调整模型、质量分数、期限或费用上限。
6. **区分给定场景与待证问题。** 首轮真实复验发现提取器把用户给定的团队迁移场景当成外部事实，导致研究员反复求证。v20 按原文位置识别显式场景前提，保留其中的真实疑问，并支持中文与英文右括号编号，避免已由子问题完整覆盖的父条款重复分配。
   对必须保留的完整原句，去掉同种类、完全包含在该原句中的重复碎片。第四轮生成了 33 条要求，原文回放去重后为 19 条；所有原有条款的出处范围仍由相同种类的保留条款覆盖。
7. **允许有证据的局部纠正。** 受限报告写作同样使用新的证据选择规则。独立 grounding 拒绝初稿后，只允许一次带原稿、原证据及具体反馈的纠正，并重新验证；不支持的结果继续拒绝。写作规则要求准确保留动作执行者，不能把“请求执行”写成“实际执行”。
8. **给出可执行的评审协议反馈。** 事实性答案的原文见证限定为连续、保留格式的短摘录，不允许插入省略号或拼接改写；修复反馈标明具体需求、证据及错误字段。流程和格式条款允许省略空证据数组；事实条款仍被服务端强制要求提供来源。保留两次结构化尝试上限，格式异常也仅使用剩余机会修正。只有一个提交示例时，服务端绑定唯一已知 ID，并保留该绑定经过结果规范化。命令检查按输入顺序返回，数量与已有标识均匹配时允许补上省略的索引；已有未知索引不重映射。重复的行为摘要可以由逐命令检查汇总，但各命令的预期生命周期、实际生命周期与停止条件不能缺省。公式需检查持续组件跨阶段的同时存活关系；工程建议和验证清单也必须遵守来源中的实际机制，不能把状态检查写成执行屏障。
9. **分开正文与代码评审。** 真实模型多次在大型嵌套 JSON 中遗漏字段或截断输出，故将正文覆盖/引用评审与示例行为评审分成两个原生步骤。示例步骤只接收完整草稿、执行单元及相关参考片段。每个步骤的结构化尝试最多两次，仍受同一运行费用、期限和 SQL 回执约束；正文元数据修正时复用同一草稿已取得的示例判定。最终门禁合并两部分结果，任一必需检查未通过均不放行。格式修正失败时保留此前已发现的实际质量问题，不再用空白“评审不可用”覆盖反馈。
10. **无损减少重复输入。** 第六轮 95 条证据的 `claim` 与 `supporting_excerpt` 全部相同。重复发送使预算估算值达到 192,644，去掉同文副本后为 113,475（UTF-8 字节保守上界，不是提供商实际 token 数）。v20 在预算裁剪前仅合并完全相同的字段，保留不同摘要、完整原文、出处及证据 ID；部分报告路径也遵守同一规则。旧 v19 输入保持不变。
11. **修正交接中的引用格式错误。** 第七轮 Judge 将 `ev_547b14d1a07950ab252b` 抄成了 `ev_547b14d1a07550ab252b`。最终准入会拒绝错误 ID，但原协议检查没有触发修正，随后被误当成覆盖缺口。v20 将此检查提前到已有的有限协议修正阶段；修正必须返回实际提交的 ID，持续失败仍拒绝，不丢弃错误 ID 后擅自放行。
12. **保守处理结构化包装。** 接受唯一外层 JSON 代码块及同名同值的重复字段；不同值、不同 JSON 类型、截断、多对象和包裹说明文字仍拒绝。补丁扩展了此前 Gateway 修复，保留未知执行结果隔离及计费规则。遗漏“需要修改”标志时按需要修改处理；无需修改的低级别纯排版提示归为信息项，事实性缺陷仍阻断。
13. **独立核验阶段峰值和公式算术。** 运行流程首次完整通过后，人工复核发现更深的初始化并发漏项。增加一个通用边界检查，使用固定的假设性持续、临时和稳态组件需求，分别测试持续组件先启动与后启动。模型判断来源是否允许该场景，并把报告原公式转写为只含指定符号、加法、max/min 和零的表达式；程序以受限语法树计算表达式，再独立计算各阶段同时运行需求之和的最大值。模型给出的数值不参与放行，表达式不会作为 Python 代码执行。欠算或提前计入尚未启动的组件均产生阻断意见。该实现来自真实回执中的 `max(0.5, 2.0) = 2.5` 算术漏判；没有写入 Kubernetes 特定答案，也不把假设值当成测量数据。
14. **分类规则与数值运算分开核对。** 同一失败报告把“相同分类规则适用于各容器”误写为“取最高 QoS 层级”。写作与审阅要求分类结论具有自己的来源依据，不能把相邻资源段落的 max 规则套入分类；没有新增 QoS 专用规则引擎。
15. **修订反馈与原始目标保持一致。** 真实复验中，程序已发现初始化峰值欠算，但模型解释仍宣称原公式覆盖全部阶段；修订换成了稳态主导的数值，掩盖原反例。反馈现在只呈现程序算出的阶段总和，并要求保留反例的原始输入与顺序。三个假设组件的角色也明确为持续辅助、有限初始化、初始化后的主工作，防止把初始化任务映射为第二个应用。另将 v20 报告写作、评审和修订中的 `research_brief` / `topic` 投影为原始需求文本，防止生成简报引入用户和来源都未要求的 `KubeletInUserNamespace` 缺口；原始简报仍保留在运行状态用于诊断，v19 输入规则不变。
16. **允许省略无意义的空元数据，保留事实检查。** 运行 `3539d0676ac446bb8c51b0b6fd4c3a38` 的流程/格式行没有答案摘录位置，模型省略 `answer_passage_index`，却被要求显式提交 null；第一次真实响应因此浪费在无意义的格式错误上，第二次又抄错需求 ID。v20 允许这类空字段省略，无前次问题时也允许省略空的 `issue_resolutions`。已覆盖事实仍必须有真实答案、来源和明确的 `missing_aspects` 声明；缺省声明使用 null 哨兵，因此 Gateway 注入默认值、序列化和 SQL 恢复后也不会被当成已检查的空列表。已有待解决问题仍要求逐条处理。新增反例证明省略事实字段依然不能通过，v19 规则保持原样。
17. **修订保留已有正确答案的依据。** 获准续验后，运行 `2d83fa211deb49b1be486113a1770d2b` 的修订阶段裁掉了全部 Sidecar 稳定版本原文，尽管初稿已经正确回答 v1.33。`_revision_prompt()` 现在复用按草稿正文检索证据的排序，继续优先保留阻断问题所需原文。真实 84 条证据及其预算相关元数据回放表明：旧逻辑选出 45 条却没有稳定版本原文，新逻辑选出 44 条并保留完整版本原文，没有扩大上下文或截断证据。夹具为 `sidecar_revision_selection_replay.json`。
18. **独立核验按各自输入验证引用。** 上述运行的公式核验实际收到 `ev_8c02eff5e9f81ac99db6`，但合并后错误地使用正文评审输入清单验证它，生成了假的 unknown_evidence_id。经过独立边界检查验证的意见现在通过私有运行时属性传递，在正文自身来源检查之后合并；这不会扩大正文模型可以引用的证据集合。回归同时验证独立意见可合并、正文擅自引用同一未见证据仍被拒绝。公式修订反馈也要求给出适用于目标顺序的公式，不能仅把反例写成建议后继续保留已证伪的答案。
19. **协调轮次覆盖已允许的补查。** 运行 `a584ce85c3064ae282a04ea55e1e4a69` 中一次探针研究失败后被重新委派，占用了 Supervisor 轮次，资源范围尚未派发便触发 iteration_limit。旧下限只考虑“每个范围一次 + 完成”，没有考虑平台本来允许的补查。v20 的协调下限按“范围数 ×（1 + 已配置补查次数）+ 完成”计算，研究员自身迭代上限、每范围补查/无进展停止、总期限和预算继续强制执行。测试用同一脚本对比 v19 与 v20：补查后新运行能覆盖最后范围，旧恢复规则不变。
20. **报告目标不重复成为事实任务。** 后续运行将开头“研究 Kubernetes 原生 Sidecar 的生产迁移方案”独立编译为事实要求，五次质量反馈都要求这个研究员重新搜齐已分配给其他研究员的全部子问题。v20 现在把显式编号问题之前、要求产出方案/报告的非疑问开头识别为 deliverable；它仍进入报告约束和原始范围，事实子问题不减少。测试同时保留真正的前置疑问和非交付类事实要求，覆盖中英文表达。
21. **独立意见不受规范化过程污染。** 获批续验 `afc217c51425442b940428e771284054` 中，边界核验结果被缓存复用，但第一次规范化给原对象写入问题 ID；同一草稿修正正文评审元数据时，这个服务端生成的 ID 被误当成模型提交的非法 ID。现在规范化复制独立意见，保留缓存输入原样；重试仍能保留真实公式缺陷，不产生假的身份错误。新增用例先复现失败，再验证修复。
