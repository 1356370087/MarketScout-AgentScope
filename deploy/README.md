# InsightForge monitoring examples

These files are deployment examples, not a bundled managed monitoring stack.

## Enable metrics

Set the following API environment variables:

```dotenv
OBSERVABILITY_ENABLED=true
PROMETHEUS_ENABLED=true
PROMETHEUS_METRICS_PATH=/metrics
RUNS_DIR_MAX_BYTES=107374182400
```

`RUNS_DIR_MAX_BYTES=0` means unlimited and suppresses the storage quota alert.
The supplied rules and dashboard target the default
`PROMETHEUS_NAMESPACE=open_deep_research`; update their metric prefixes if the
namespace is customized.

## Prometheus scrape job

Add an API scrape job and load the provided rule file:

```yaml
global:
  scrape_interval: 30s

rule_files:
  - /etc/prometheus/rules/insightforge-alerts.yml

scrape_configs:
  - job_name: insightforge
    metrics_path: /metrics
    honor_labels: true
    static_configs:
      - targets: ["api:2024"]
```

Mount `deploy/prometheus/alerts.yml` at the `rule_files` path. Keeping
`honor_labels: true` preserves the service's bounded provider, model, role, and
operation labels. The application deliberately does not expose run IDs, user
IDs, paths, prompts, or URLs as metric labels.

Validate rule changes before deployment:

```bash
promtool check rules deploy/prometheus/alerts.yml
```

## Alert delivery

Prometheus sends firing alerts to Alertmanager. Configure the receiver in
Alertmanager rather than embedding credentials in this repository. A minimal
Prometheus connection looks like this:

```yaml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
```

Route `severity=warning` to the operational on-call channel. Tune `for` windows
and thresholds only after collecting a representative workload baseline.

## Grafana

Import `deploy/grafana/dashboard.json`, then select the Prometheus datasource.
The dashboard covers run throughput and duration, token usage and estimated
cost, prompt-cache hits, research queue depth and wait, rate limits and retries,
durable storage capacity, and observability export failures.

## Runtime topology and maintenance

Run one API worker per deployment instance. API admission counters, SSE
connection limits, and the in-memory run registry are process-local. SQLite uses
WAL with a five-second busy timeout, but trace writes remain best-effort with
multiple workers.

Report files are generated by the separate `publisher-worker` Compose service.
It shares only the `research-runs` volume with the API, runs without a network,
uses an unprivileged container user, does not receive `.env` provider
credentials, and uses file locks plus expiring job leases for restart recovery.
The API container runs as the same unprivileged user (`uid=10001`), so the
`0600` job and artifact files stay owner-private while remaining readable by
both sides across the shared volume.

### Upgrading existing volumes to the shared API uid

Images built before the API ran as `uid=10001` left `research-runs` and
`document-data` owned by root. After upgrading, run once per host:

```bash
docker compose down
docker compose run --rm --user 0 api \
  chown -R 10001:10001 /data/runs /data/documents
docker compose up -d
```

(`sandbox-control` needs no chown: its directory only hosts the controller
socket, which is recreated at startup with cross-uid connect permissions.)
API capabilities report the Worker as degraded
when its shared-volume heartbeat becomes stale; queued jobs remain durable and
resume when the Worker returns.

When the Worker is launched directly on native Windows, `asyncio` cannot install
the same SIGTERM handler used in Linux containers. A forced process termination
therefore recovers an in-flight publication after its configured lease expires.

Publication jobs, events, and generated files live inside each Run directory,
so the existing terminal Run retention sweep removes them together with the
owning Run. There is no separate publication retention policy.

For advanced memory, use an external daily timer or enable the commented
`memory-maintenance` Compose service. Its loop holds one file lock and exits
immediately if another maintenance process already owns it.

Sandbox V7 never injects provider credentials into Worker containers. Build
`sandbox-worker-image`, run
`python -m open_deep_research.sandbox.pin_image`, then set
`SANDBOX_ENABLED=true`, `ENABLE_ASYNC_RESEARCH=true`, an immutable policy image
digest, and a shared `SANDBOX_ROOT_SIGNING_KEY`, then start the Compose
`sandbox` profile. Run `python -m open_deep_research.sandbox.doctor` before
admitting traffic.

### E2E domain pre-approval

E2E harnesses should preset the research domains they will hit via
`SANDBOX_EGRESS_ALLOW_DOMAINS` (comma-separated, `*.gov.cn` / `**.edu.cn`
wildcards allowed). Matching domains are allowed outright — no classifier, no
human `allow_once` — because approval latency otherwise eats the bounded
research window while the researcher's react budget is refunded but its
wall-clock keeps running. The merged allowlist participates in the frozen
per-run policy digest, so a run's egress posture stays auditable. Keep the
variable unset in production; real deployments should rely on the TOML policy
and the approval flow.

## Compose observability profile

The bundled stack brings up Prometheus, Grafana, an OTel Collector, and Jaeger
behind a compose profile (default deployments stay unchanged):

```bash
docker compose --profile observability up -d
```

- Prometheus scrapes both `api:2024` (app metrics, `open_deep_research_*`
  prefix) and `litellm-proxy:4000` (gateway deployment health, fallbacks,
  cooldowns) using `deploy/prometheus/prometheus.yml`; alerts load from
  `deploy/prometheus/alerts.yml`.
- Grafana (default `http://localhost:3001`, admin password from
  `GRAFANA_ADMIN_PASSWORD`) auto-provisions the existing InsightForge
  dashboard plus a LiteLLM gateway dashboard.
- The OTel Collector forwards OTLP traces to Jaeger
  (`http://localhost:16686`).

### Gateway-side traces (LiteLLM otel callback)

Enable with two extra env vars on the deployment (the OTel exporter is
already installed in the proxy image, and `config/litellm.otel.yaml` is the
callback-enabled twin of the main config, guarded by a parity test):

```dotenv
LITELLM_CONFIG_PATH=/app/config/litellm.otel.yaml
LITELLM_OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
```

Application spans already propagate `traceparent` on every gateway request,
so app and gateway spans land on the same trace in Jaeger. Message content
stays off (`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=no_content`);
only flip it after reviewing the privacy implications.

To export app-side spans through the same collector set `OTEL_ENABLED=true`
and `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318`.

Security note: LiteLLM's `/metrics` endpoint is unauthenticated. Keep the
4000 host port unmapped in untrusted networks (compose maps it only for the
offline-evaluation workflow).

Document chunking uses a deterministic 3200-character window with 480-character
overlap (approximately 800/120 English tokens). This is intentional for stable
Chinese offsets and reproducible reindexing across embedding model changes.

## Remote PaddleOCR

The document worker supports the PaddleOCR inference API exposed by
`POST /ocr` (JSON request). Configure the worker through `.env`:

```dotenv
DOCUMENT_RESEARCH_ENABLED=true
DOCUMENT_OCR_ENABLED=true
DOCUMENT_OCR_MODE=remote
DOCUMENT_OCR_URL=http://172.22.208.30:8080/ocr
DOCUMENT_OCR_API_KEY=
DOCUMENT_OCR_FILE_TYPE=0
DOCUMENT_OCR_TIMEOUT_SECONDS=120
```

The worker sends PNG bytes as standard base64 in the `file` field and uses
`fileType=0` for image pages. An API key, when set, is sent as a Bearer token.
The response is read from `result.ocrResults[*].prunedResult.rec_texts` and
`rec_scores`; non-zero `errorCode` values become durable ingestion failure
codes. In Compose, `document-worker` is attached to the default network so the
configured LAN endpoint is reachable; restrict that egress at the host or
network firewall in production.

The worker uses `LITELLM_SERVICE_KEY` for ingestion embeddings. Query-time
embeddings require the Run-scoped virtual key and fail closed when no Run
context is present; the master key is never used for document search.
