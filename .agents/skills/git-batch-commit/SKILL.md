# 按职责整理 Git 提交

目标是形成范围准确、便于评审和回滚的提交。以当前仓库约定、实际差异和用户授权为准；一个职责可以跨多个目录，单一职责无需硬拆。

## 任务模式与授权

- **分析或方案**：审查改动、生成分批方案，不暂存、不提交、不推送。审查或修改本 skill 不等于授权提交整个工作区。
- **仅提交**：用户要求“提交一下”“帮我提交代码”且没有推送授权时，只完成本地提交。
- **提交并推送**：用户明确要求或此前已授权时，在相同范围和目标内完成提交与推送。
- **仅推送**：先核对已有待推送提交，不自动把未提交改动做成新提交。
- 已明确的授权在会话内持续有效。先展示具体范围、批次和目标，再按授权继续；不要求固定的两轮确认。只有改动归属、目标仓库或分支等必要信息无法确定，或新操作超出授权时，才询问具体缺失项。

## 检查仓库与改动

先读取适用的 `AGENTS.md`、贡献指南、提交模板、提交消息校验和分支策略，再参考近期 `git log`。没有配置的工单、签名、PR 或检查要求，不自行当成强制规则。

独立读取可以并行，暂存、提交和推送按依赖顺序执行。至少核对：

- `git status --short --branch`、`git status --porcelain=v1`：区分暂存区与工作区；状态的两列分别表示 index 和工作区，不把一个 `M` 笼统当作全部修改。机器解析使用 `-z`，正确处理空格和重命名路径。
- `git diff --stat` 和 `git diff --cached --stat`：分别了解未暂存、已暂存改动的规模。
- `git diff -- <路径>` 和 `git diff --cached -- <路径>`：阅读两种实际差异，包括新增、删除、重命名和部分暂存。另行阅读属于本次范围的未跟踪文件；二进制文件核对用途和来源。
- 当前 HEAD、`git branch --show-current`、已有 upstream 和远程配置：推送时再核对目标分支、同步状态和待推送历史。

记录本次操作前的 HEAD、已有暂存内容及部分暂存边界。现有暂存内容不自动等于本次授权范围，不清理其他任务的改动。遇到冲突、进行中的 merge/rebase/cherry-pick 或未明确目标的 detached HEAD，先说明状态；不擅自中止操作或改写历史。

按仓库规则识别本地配置、凭据、文档存储和生成目录，不回显真实秘密。本项目的 `.runs/`、`.documents/`、`.playwright-cli/`、`.playwright-mcp/`、`.pnpm-store/`、`output/` 以及本地 IDE 状态属于重点检查对象；项目共享 IDE 配置不能一概排除。忽略规则不能代替对已跟踪文件的审查，已跟踪产物的删除也要确定职责和范围。不要为提交流程顺手改写 `.gitignore`。

## 按行为和依赖分批

每批描述一个完整的行为变化或维护目的，说明涉及内容、依赖顺序和对应验证：

- 功能或修复与其必要测试、前后端契约、配置、迁移及说明放在同一职责单元。独立测试设施、无关重构或文档工作可以另拆。
- 按依赖顺序提交。每个提交应在前序提交之上可构建或通过相关最小验证，不能引用后续批次才引入的符号、字段或迁移。
- 同一文件包含多个独立职责时，按可靠的 hunk 边界暂存，可用 `git add -p` 或经检查的补丁。不要把交互能力不足当成整个文件天然自洽的理由；无法可靠拆分或职责强依赖时合并并说明取舍。
- 以一个提交及其前序依赖是否便于评审和回滚为准，不按目录数量拆分。不可逆迁移或回滚限制需要说明。

提交执行模式下，先向用户展示简明方案：每批标题、文件或 hunk 范围、顺序、检查方式、排除项，以及已授权的推送目标。方案模式到此结束；已获提交授权则继续执行。

## 提交消息

优先遵守仓库已有规则。未定义时使用 Conventional Commits：`type(scope): 中文摘要`；scope 为业务领域的英文小写名，摘要描述具体变化，使用明确动词，避免“更新代码”“完善功能”等空泛措辞。

Conventional Commits 允许省略 scope。存在明确领域时保留 scope，纯测试也可写 `test(native)`、`test(knowledge)`。沿用已有的 `research`、`runtime`、`native`、`api`、`frontend`、`report` 等领域名，不机械地把所有跨目录改动归为 `core`。

| type | 判定依据 |
| --- | --- |
| `feat` | 新增对外能力或行为 |
| `fix` | 修复错误行为 |
| `refactor` | 重组实现，对外行为保持一致 |
| `perf` | 改善性能 |
| `test` | 独立新增或调整测试及测试设施 |
| `docs` | 独立文档变更 |
| `build` | 构建系统、依赖及打包维护 |
| `ci` | 持续集成配置 |
| `style` | 不改变行为的代码格式调整 |
| `chore` | 其他维护工作 |
| `revert` | 撤销既有提交，说明被撤销的提交及原因 |

type 按目的和行为判定；配置或依赖变更也可能是某个 `feat` 或 `fix` 的组成部分，不能仅凭文件名判为 `chore`。

标题长度服从仓库校验；未定义时建议控制在 72 个字符以内且不加句末句号。这是默认建议，不是 Conventional Commits 的强制长度。简单变更只需标题，复杂变更补充原因、关键行为和实际验证，标题与正文之间留空行。下面是模板，按需替换并删除不适用项，不能把占位文字直接提交：

```text
type(scope): 中文摘要

说明触发问题、变更原因和结果。
必要时说明兼容性、部署迁移或回滚限制。
验证：实际检查命令与结果；未执行则说明原因。

Refs: <真实工单编号>
```

存在破坏兼容性的变更时，用标题中的 `!` 或 `BREAKING CHANGE:` footer 标识，并说明影响和迁移方式；可以同时使用两者。实际要关闭工单时才使用 `Closes:`，不编造编号、验证结果或签名。签名和 DCO trailer 仅按现有组织要求处理，不绕过提交钩子或消息校验。

本项目的标题示例：`fix(runtime): 修复恢复账本的租约写入检查`、`feat(research): 增加官网来源审批`、`test(knowledge): 补充资料版本冻结回归`。具体标题必须来自实际差异，不沿用旧 QueryEngine 或文件任务池示例。

## 选择和记录验证

检查以当前 `AGENTS.md`、`pyproject.toml`、`frontend/package.json` 和 CI 配置为依据。执行与改动相关的最小必要检查及仓库要求的检查，不把验证仅当作提醒，也不默认对所有改动跑全量测试或 E2E。

本项目可按范围选择：

- 后端：设置正确的 `PYTHONPATH` 后执行 `uv run pytest <相关测试文件>`；原生运行时边界变化时按需执行 `uv run python -m open_deep_research.migration_check --check all`。
- 前端：在 `frontend/` 按改动选择 `pnpm lint`、`pnpm exec tsc --noEmit`、`pnpm test`、`pnpm build`；E2E 按相关用例及其依赖准备，结束后只关闭本次启动的服务。
- 文档或 skill 指令变更：做相应结构、内容和差异检查，不为这类变更新增镜像实现的测试。当前项目未配置 Ruff，不把 `ruff check` 当作既有必选项；类型检查也要区分已有债务与新问题。

验证要对应将形成的提交及其前序依赖。完整混合工作区通过不能证明中间提交通过；可能依赖后续批次时，使用隔离快照核对导入、构建或关键回归，或调整分组。报告实际验证对象，不能把工作区验证冒称为每批验证。

记录命令、结果和环境前提。检查失败先判断是否与本批有关，不顺手修复范围外问题；必需检查失败时停止受影响提交或推送。用户明确要求先保存本地进度时，可在授权范围内提交并标明未通过或未验证；不据此跳过受保护分支的必需检查。缺少数据库、模型或 E2E 环境应报告证据不足，不记为通过或研究质量失败；真实模型调用与外部数据提交须有对应授权。

## 逐批提交

每批依次执行，前一步失败时不继续后续提交或推送：

1. 确认现有暂存内容与本批一致。需要重组时，只对已授权整理的具体内容操作，保留原有部分暂存边界；必要时先保存其补丁，再对明确路径使用 `git restore --staged -- <路径>` 并按 hunk 恢复。对未授权调整的范围外暂存内容，保留原样；不能安全隔离时说明具体冲突，暂停受影响批次。禁止整体 `git reset` 或清空暂存区来重新分组。
2. 用 `git add -- <明确路径>` 或 hunk 暂存本批内容，路径正确引用。新增、删除和重命名都必须属于本批；不使用根目录范围的 `git add .` 或 `git add -A`。
3. 核对**整个暂存区**的 `git diff --cached --name-status` 和 `git diff --cached`，并执行 `git diff --cached --check`。文件和 hunk 都必须与本批方案一致；只检查刚添加的文件不能证明本批完整性。发现夹带内容、重复内容或遗漏依赖时先修正方案或暂存，不能直接提交。
4. 完成上述适用验证，按真实结果定稿消息。写到本次创建的唯一系统临时文件，使用 UTF-8、无 BOM 和真实换行，再执行 `git commit -F <临时文件绝对路径>`。不固定写入 `.git/BATCH_MSG`：worktree 的 `.git` 可能是文件。完成后仅删除本次消息临时文件。
5. 检查命令退出码及生成的提交差异、哈希和剩余状态。钩子修改了文件或执行期间出现新改动时重新审查；不自动加入额外改动，不用 `--no-verify`，不擅自 amend 或改写已有提交。失败时保留已经成功的提交并报告停止位置。

## 按授权推送

只有推送模式才执行。目标优先使用用户指定的仓库和分支，其次使用已核对的 upstream；没有 upstream 时核对唯一可确认的目标，无法判断则询问。不能只因为存在名为 `gitee` 的远程就覆盖已有目标，不自行新增远程或默认直推 `main`。按仓库实际分支保护和 PR 规则处理，不凭空强制创建 PR。

推送前获取目标远程状态，审查目标分支到当前 HEAD 的**全部待推送提交**及分歧，包含本次之前的未推送提交。超出已授权范围时先说明具体内容；不能把只核对新批次当作推送范围检查。遵守目标分支要求的验证，不能仅因本地已提交就绕过。

向确认的单一分支显式推送，如 `git push --no-follow-tags <远程> HEAD:refs/heads/<目标分支>`，不顺带推送其他分支或标签：

- 非快进拒绝：获取并解释分歧；仅在已有授权覆盖时执行合并或 rebase，不自动 stash 用户改动，不使用 `--force` 或 `--force-with-lease`。
- 认证或网络失败：报告具体阻碍，使用已配置的凭据助手或 SSH，不索取令牌明文或无限重试。结果不确定时先查询目标 ref，再判断是否需要重试。
- 成功后核对远端目标 ref 与预期提交；无法完成二次查询时如实说明已收到的推送结果及确认限制。

## 完成报告

报告每批哈希、标题、实际验证结果，以及是否推送、目标和仍未处理的改动或阻碍。没有文件改动时仍需区分是否有已有待推送提交；仅分析或仅提交模式按各自范围结束，不宣称整个工作区必然干净。
